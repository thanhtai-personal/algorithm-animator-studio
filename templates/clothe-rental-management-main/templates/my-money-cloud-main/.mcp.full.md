# MCP_FULL – My Money Cloud
**Unified Architectural Constitution (Non-Redundant)**

## 2. Project Identity

- Offline-first personal finance application
- Platforms:
  - Web: Next.js (App Router)
  - Mobile: React Native / Expo

---

## 3. Core Architecture (Immutable)

### 3.1 Layering (Strict)

```
Component
 → Hook
   → Query (TanStack Query)
     → Service
       → API / Supabase
```

### 3.2 Dependency Law
- Dependencies flow **downward only**
- No upward or cross-layer imports

---

## 4. Responsibility by Layer

### Components
- UI rendering only
- No business logic
- No data fetching
- No store access
- No side effects

### Hooks
- Orchestrate business logic
- One responsibility per hook
- Never mix domains or concerns

### Queries
- Manage server request lifecycle
- Fetch, retry, cache, invalidate
- Call exactly one service capability

### Stores (MobX)
- Own UI-visible state
- Own persistence
- Expose intent-based actions only

### Services
- Encapsulate API calls or server business logic
- No UI or framework concerns

### Adapters
- Map API ↔ DTO
- No business logic
- One direction only

---

## 5. State & Data Model

### 5.1 Client State
- MobX is the only client-side state manager
- React subscribes via `observer`
- No Provider / inject pattern
- No class components

### 5.2 Server State
- All remote data flows through TanStack React Query
- Services are called **only** inside queries/mutations

### 5.3 Single Source of Truth
- React Query owns **request lifecycle**
- MobX owns **UI-visible state**

---

## 6. Store-First Hydration Rule (Critical)

### Mandatory Flow
1. React Query executes request
2. `onSuccess` merges data into store
3. Store persists data locally
4. UI renders **only from store**
5. No duplicate data store.

### Forbidden
- Rendering from query data
- Skipping store merge
- Multiple sources of truth
- 1 value in 2 store

---

## 7. Feature Ownership (Client-side)

```
features/<feature>/
 ├─ components/
 ├─ hooks/
 ├─ queries/
 ├─ stores/
 ├─ adapters/
 ├─ utils/
 ├─ types/
 ├─ constants.ts
 └─ index.ts
```

Rules:
- Features are isolated
- No feature imports another feature’s internals
- No server logic inside features
- server logic in `src/server`

Shared UI/Logic:
- `src/components` → atoms & molecules only
- `src/types` -> types that use on both server side and client side or type for many features.
- `src/utils` -> global util functions
- `src/constants` -> global constant

---

## 7.1 Feature Internal Structure & Boundary (Mandatory)

### Hooks
- One hook = one responsibility
- Separate by role: query, mutation, sync, form
- No util logic inside hooks

### Feature Utilities
- All domain-specific helpers live in `features/<feature>/utils`
- One utility responsibility per file
- Duplication allowed for clarity

### Feature Constants
- `features/<feature>/constants.ts`
- Domain-only semantics
- No cross-feature constants

### Feature Types

```
features/<feature>/types/
```

Used for:
- UI
- Hooks
- Stores
- Client-only concerns

Rules:
- Feature types are not shared across features
- Feature types are not imported into server code

---

## 7.2 Global Utilities & Constants (Cross-Feature, Controlled)

### Global Utilities

```
src/utils/
```

Rules:
- Pure functions only
- No feature semantics
- No framework dependency
- No side effects

### Global Constants

```
src/constants/
```

Rules:
- System-level or infrastructure-level constants
- No business/domain meaning
- Immutable at runtime

### Decision Rule

1. Domain-specific → feature util / constant
2. Used by ≥2 features with same meaning → consider global
3. Domain-sensitive behavior → must stay in feature

### Promotion Rule
- At least 2 real usages
- Same semantic meaning
- Promotion is refactor-only

---

## 8. Shared Types (Client–Server Contract)

```
src/types/
```

Rules:
- Pure data structures only
- Used by:
  - Server services
  - API routes
  - Client queries
- No UI, store, or framework dependency

Forbidden:
- Import feature types here
- Import server-only types into client

---

## 9. Server Ownership (Web)

```
app/api/              # routing only
server/
 ├─ services/         # business logic
 ├─ data-access/      # Supabase only
 ├─ utils/
 └─ types/
```

Rules:
- Supabase access only in `server/data-access`
- `app/api` delegates to `server/services`
- Client must never import `server/**`

---

## 10. Offline-first & Sync Model

- Offline mutations enqueue into `offlineQueueStore`
- UI updates optimistically
- Sync replays when online
- Server response is final source of truth
- Always merge, never blind overwrite

Offline is a **first-class case**, not an edge case.

---

## 11. Realtime Sync

- Supabase Realtime updates stores
- Events merge carefully
- React Query refetch is authoritative reconciliation

---

## 12. Next.js App Router Boundary

`src/app` is routing & server-boundary only.

Allowed:
- Routes, layouts, metadata
- Import Screen components

Forbidden:
- Business logic
- Queries
- Stores
- Feature UI rendering

---

## 13. Atomic UI Rules

### Atoms
- No logic
- No hooks
- No stores

### Molecules
- Compose atoms only
- Data via props

### Organisms
- Feature-owned
- May use feature hooks
- Never reused across features

### Screens
- Page composition only
- No orchestration
- No hooks

---

## 14. Single Responsibility per File (Mandatory)

- One file = one primary responsibility
- Applies to all layers

If a file requires more than **one sentence** to explain, it is invalid.

---

## 15. Hook Discipline

- One hook = one responsibility
- Do not mix fetching, mutation, orchestration, formatting

---

## 16. Store Discipline

- One domain per store
- Actions express intent
- Store owns persistence

Forbidden:
- Generic state bags
- Cross-domain stores

---

## 17. Query & Service Discipline

### Queries
- One query or mutation group per file
- Wrap exactly one service capability

### Services
- One capability per service
- No mixed responsibilities

---

## 18. Utility & Adapter Discipline

- One clear purpose per file
- No grab-bag utils
- Duplication allowed
- No speculative abstraction

---

## 19. Abstraction Rules

- Do not abstract until **two real use-cases exist**
- No future-proof interfaces
- Abstract only when behavior diverges

---

## 20. Naming Discipline (Domain-first)

Prefer:
- `syncPendingTransactions`
- `enqueueOfflineOperation`

Avoid:
- `handleSubmit`
- `doStuff`
- `processData`

---

## 21. Error Handling & Failure Modes

- Errors must be explicit
- Never swallow errors
- Distinguish client vs server
- Offline, retry, partial data must be deliberate

---

## 22. Control Flow Rules

- Prefer early returns
- Avoid deep nesting
- No hidden side effects

---

## 23. useEffect Restriction

Allowed:
- Subscriptions
- Lifecycle-bound side effects

Forbidden:
- Orchestration
- Cross-layer glue logic

---

## 24. Refactoring Rules

- One refactor = one goal
- Never refactor + add feature
- Preserve behavior

---

## 25. Anti-patterns (Forbidden)

- God hooks or stores
- Passing stores through props
- Boolean flag explosion
- Premature abstraction

---

## 26. Mandatory Decision Order

Before writing code, decide:

1. Correct layer
2. Ownership
3. Data lifecycle
4. Failure modes
5. Extension points

Skipping this order is a violation.

---

## 27. Final Principle

> Code must read like a **system**, not a script.

Architecture integrity outweighs delivery speed.
