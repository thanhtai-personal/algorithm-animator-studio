# MCP_FULL – KATA Clothing Rental Platform
**Unified Architectural Constitution (V2)**

## 1) Purpose
This document is the non-negotiable architecture constitution for implementation tasks.
If any task/doc conflicts with this file, this file wins.

## 2) Project Identity
- Domain: clothing rental + sales + showroom operations + makeup + mini-app channels.
- Monorepo runtime apps:
  - `apps/web`: Next.js admin UI (legacy API routes are compatibility-only).
  - `apps/server`: NestJS API target (new backend source-of-truth).
  - `apps/mobile`: Expo mobile client.
  - `apps/zalo-mini-apps/*`: Zalo Mini App clients.
- Data platform: Supabase (Postgres + Auth + RLS + Storage + Realtime).

## 3) Architecture Modes

### 3.1 Current mode (Transition)
- Web still contains legacy API routes in `apps/web/src/app/api/**`.
- Nest server exists but is not yet complete for all domains.
- Effective policy from now:
  - only `apps/server` is allowed to access Supabase database.
  - non-server runtimes must call `apps/server` API.

### 3.2 Target mode (Mandatory for new design)
- `apps/server` is the business API source-of-truth.
- `apps/web` is UI-first; web API routes become compatibility adapters only (temporary).
- All clients call Nest API via environment-driven base URL.
- Only `apps/server` connects to Supabase database.

## 4) Core Layering Contracts

### 4.1 Client layering (strict)
```text
Component -> Hook -> Query (TanStack Query) -> Service -> API
```

Rules:
- Components never call HTTP/service directly.
- Queries/mutations own remote request lifecycle.
- Services encapsulate API transport details only.

### 4.2 Backend layering (`apps/server`, strict)
```text
Controller -> Application Service -> Data-access/Repository -> Supabase
```

Rules:
- Controllers do routing/validation/response mapping only.
- Business logic belongs in application service.
- Data-access is the only layer that touches Supabase queries in `apps/server`.

### 4.3 Dependency law
- Dependencies flow downward only.
- No upward imports, no cross-layer leakage.

## 5) State Ownership Contracts

### 5.1 Client state
- MobX owns UI-visible state + local persistence.
- React subscribes through `observer`.

### 5.2 Server state
- TanStack Query owns fetch/cache/retry/invalidate lifecycle.

### 5.3 Store-first hydration rule
1. Query fetches data.
2. `onSuccess` merges into store.
3. UI reads from store.

Forbidden:
- Rendering directly from query data for stateful domain screens.
- Duplicate source-of-truth between query cache and store state.

## 6) Web Boundaries (`apps/web`)

### 6.1 Allowed in `src/app`
- Route/layout composition, metadata, route-level middleware behavior.

### 6.2 Forbidden in `src/app`
- Heavy business logic, direct Supabase business query logic.
- Any direct Supabase database access from web route handlers.

### 6.3 Web API transition policy
- New business endpoints MUST be added in Nest (`apps/server`).
- Web `app/api` can only host temporary forwarding/compatibility routes when required.

## 7) Server Ownership Rules

### 7.1 During transition
- Existing web server layers are legacy and decommission-target:
  - `apps/web/src/server/services/**`
  - `apps/web/src/server/data-access/**`
- No new DB/business logic may be added in those legacy web layers.
- Legacy web routes (if still needed) must forward to `apps/server`.

### 7.2 Target ownership
- Business APIs move to `apps/server/src/**` by domain slices.
- Domain logic must not be duplicated between web legacy API and Nest API.

## 8) Data Platform & Security Contracts

### 8.1 Supabase access
- `apps/server` is the only runtime allowed to query Supabase database.
- `apps/web`, `apps/mobile`, and `apps/zalo-mini-apps/*` must access business data via `apps/server` API.
- Do not expose service-role operations to client runtime.

### 8.2 Auth and RBAC
- Auth is Supabase-based.
- Authorization is enforced with RLS + service-layer guards.
- Branch-scoped access is mandatory for branch-bound domains.

### 8.3 Feature flags
- DB-backed feature flags (`system_settings`) are authoritative for module enablement.
- Runtime env flags must not silently contradict DB flags.

## 9) Offline / Realtime / Voice Contracts

### 9.1 Offline-first
- Offline is first-class; do not assume always-online flows.
- Sync/replay flows must avoid silent data loss.

### 9.2 Realtime
- Realtime updates are near-real-time signals.
- Query refetch remains reconciliation authority.

### 9.3 Voice
- Reuse shared voice primitives per app.
- Prevent stale async voice results from mutating closed/reset UI contexts.

## 10) Feature Isolation Rules

### 10.1 Feature layout
`features/<feature>/components|hooks|queries|services|stores|types|utils|constants.ts|index.ts`

### 10.2 Isolation
- No feature imports another feature’s internals directly.
- Cross-feature utilities belong in shared layers only when truly generic.

## 11) Migration Rules (Web API -> Nest API)
- Migrate endpoint-by-endpoint with contract parity.
- Keep compatibility window until all callers are cut over.
- Remove legacy endpoints only after:
  - caller cutover complete,
  - regression pass,
  - rollback path documented.

## 12) Task Compliance Standard (Mandatory)
All new tasks must include:
1. Architecture Impact
2. Current State vs Target State
3. Boundary Rules
4. Compatibility & Migration Strategy (if cutover)
5. Done Criteria (Architecture)
6. Regression Scope

Reference: `docs/architecture/011_task_architecture_compliance_standard.md`

## 13) Quality Gates

### 13.1 Minimum checks per touched app
- Web: `npm run lint`, `npm run typecheck` (or equivalent documented command).
- Server: `npm run lint`, `npm run build`.
- Mobile/Mini-app: lint/typecheck/build as applicable.

### 13.2 High-risk domains
Auth, RBAC, offline sync, payment/order settlement, and voice flows require explicit regression notes.

## 14) Explicitly Forbidden
- Adding new business endpoints only in web route layer when Nest path exists.
- Cross-layer shortcuts (component -> service/http direct, controller -> repository bypass service).
- Silent contract breaking changes during migration.
- Silent privilege broadening in auth/RLS changes.
- Any direct Supabase database query from runtimes other than `apps/server`.
